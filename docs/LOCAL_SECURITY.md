# Local security model

Top-level browser GET navigations to `/` and `/index.html` may open the public Console shell from another site. This exception requires Fetch Metadata identifying a document navigation; it never applies to `/v1/` API requests, subresources, or writes.

Agentree is a single-user local application listening only on loopback. An ordinary HTTP request has no human authority, even with a localhost Host, a trusted Origin, or spoofed actor fields. Human operations require a local capability; agent operations require a session capability. There are no accounts, passwords, manual token copying or browser pairing.

## Automatic human access

Gateway creates a random capability beside its database at `gateway.sqlite.human-token`. It is an owner-only regular file (0600); symlinks and files accessible to other users are rejected. Keep its containing data directory private (0700). Trusted local launchers and HTTP CLI commands read this file automatically and send it as a bearer credential, only to loopback HTTP destinations without following redirects. Direct SQLite CLI commands retain their trusted filesystem boundary. Managed environments carrying `HARNESS_SESSION_ID` or `HARNESS_SESSION_TOKEN` cannot use these human helpers or the direct database CLI. These environment checks prevent accidental identity changes; they are not an OS sandbox.

Running `agentree` starts or reuses the daemon, authenticates locally, and requests a one-use Console ticket. It opens the Console with the ticket in a URL fragment, which is not sent in HTTP requests or Referer headers. The Console removes the fragment immediately and POSTs it to `/v1/console-session`. A successful exchange consumes the ticket and sets a random HttpOnly, SameSite=Strict cookie. Tickets expire after 60 seconds; cookies expire after 12 hours. Both are stored as hashes in daemon memory and are invalid after restart. Open `agentree` again to restore browser access. The persistent local human capability and native session credentials survive restart. Headless startup prints the same short-lived launch URL; treat it as a temporary secret.

Neither static assets nor `/health` issue credentials. All `/v1` reads and writes, including SSE, require credentials except the capability-bearing ticket exchange. No GET endpoint issues credentials. The public health response includes the database path so the local launcher can reject a daemon using a different data directory. API responses containing credentials are `no-store`; tokens never appear in query strings, task records, or audit events. An explicit Authorization header always takes precedence over a browser cookie, including invalid or agent credentials.

## Browser boundary

Exact Host validation against localhost/127.0.0.1 and the actual listener port blocks DNS rebinding. Origin must equal the Gateway origin or an explicitly configured loopback HTTP Console origin. Cross-site Fetch Metadata without Origin is rejected, including GETs; browser writes with Fetch Metadata require an allowed Origin. Missing Origin is allowed for native HTTP clients, but never grants authority. SameSite cookies supplement these checks; HttpOnly keeps the browser credential out of Console JavaScript. Frame denial and a no-referrer policy protect the launcher flow. HTTP cookies have no port isolation: other services on the same loopback hostname must be trusted not to capture cookies during browser visits. Local HTTP is deliberately unsupported as a remote transport.

Built Console assets use the Gateway origin. Development origins are disabled by default. For Vite, explicitly set `GATEWAY_CONSOLE_ORIGINS=http://localhost:5173` on the daemon and `AGENTREE_CONSOLE_URL=http://localhost:5173` on the launcher. Use live mode and `VITE_GATEWAY_URL=http://localhost:8787`; use matching loopback hostnames for Console and Gateway so SameSite cookies work. Credentialed CORS allows only the exact configured origins. Opting in trusts the code served by that development server. Cross-origin SSE uses the same cookie and Origin protections.

## Native session boundary

Only a human capability can register sessions and receive a new random session token. SQLite stores token hashes. Native requests derive their actor from the credential, never from body fields, native IDs, process IDs, or Origin. A session cannot act as human, use another session's resources, change Main, restore Main, assess conflicts, approve tools, or dispatch tasks. Native identity claims in tool decisions must match the bound session. Activity must be observed, must belong to that session and workspace, and cannot use the Gateway audit source.

A session can report its own termination, fetch its own corrections, and claim or acknowledge only its own tasks. A human can request termination; pending approvals settle to denial and inactive sessions cannot execute approved tools. End reporting remains idempotent so a launcher can report exit after a kill request. Approval request IDs are scoped to a session and retries with different tool/input conflict. Approval deadlines and session state are rechecked before returning permission. Tool enforcement still depends on the attached native pre-execution hook; approval is not evidence of execution success.

Process bindings validate discovered PID, birth time, runtime, and uniqueness. They are session-authenticated visibility claims, not proof that the caller owns an OS process, and grant no process-control authority. Task dispatch is human-only; native delivery evidence is session-bound and remains a claim by that runner. Restart never automatically redelivers tasks with uncertain native outcomes.

## Threat model and limits

Blocked: anonymous localhost HTTP callers (including coding agents dropping their token), session holders trying human operations or other sessions' resources, hostile browser origins, cross-site browser requests, DNS rebinding, invalid credentials falling back to cookies, and replayed/expired Console tickets. Capability possession grants authority; browser headers alone do not.

Outside the trust assumptions: malicious code with equivalent OS-user filesystem/process privileges can read the human capability or another session's token, inspect environments, remove managed markers, modify the database, or replace the application. Capability files, the database, and native credential files must be inaccessible to agent sandboxes if strong isolation is required. Compromised trusted Console/dev-server code, browser extensions with sufficient privileges, and local malware are also outside this boundary. Cookies and capability tokens do not prove a physical human is present. Agentree supplies an HTTP authority boundary, not an OS sandbox. Remote listeners, reverse proxies, shared-user isolation, and remote authentication are unsupported.

Use one private data directory: `AGENTREE_HOME`, then `GATEWAY_DATA_DIR`, then `~/.local/share/agentree`. The fixed port bind prevents duplicate listeners. A conflicting service or database fails explicitly. CLI subcommands retain their `--db` override. Build backend and Console for normal use. No external authentication service is needed.
